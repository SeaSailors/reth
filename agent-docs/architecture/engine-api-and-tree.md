# Engine API And Engine Tree

This document explains how Reth wires and serves the Ethereum Engine API ("authrpc") and how the Engine Tree processes Engine API messages.

It focuses on two related subsystems:

- Engine API server layering: `reth-rpc-api` trait definitions -> `reth-rpc-engine-api` implementation.
- Engine Tree: the in-process handler that processes `engine_newPayload*` and `engine_forkchoiceUpdated*` messages, maintains canonical state, and emits events/metrics.

## Where This Lives (Key Files)

- RPC trait definitions (JSON-RPC surface): `crates/rpc/rpc-api/src/engine.rs`
- RPC implementation (handler struct + wiring): `crates/rpc/rpc-engine-api/src/engine_api.rs`
- Engine tree handler: `crates/engine/tree/src/tree/mod.rs`
- Engine tree metrics: `crates/engine/tree/src/tree/metrics.rs`
- Engine API types/traits shared across crates: `crates/engine/primitives/src/lib.rs`, `crates/engine/primitives/src/message.rs`
- Payload building store/handle: `crates/payload/builder/src/service.rs`
- Node wiring (launch and RPC): `crates/node/builder/src/launch/engine.rs`, `crates/node/builder/src/rpc.rs`

## Layering: RPC Trait -> Engine API Implementation

Reth models JSON-RPC namespaces as `jsonrpsee` traits in `reth-rpc-api`, and implements them in separate crates.

### 1) The RPC Trait Layer (`reth-rpc-api`)

`crates/rpc/rpc-api/src/engine.rs` defines the `engine_` namespace as a `jsonrpsee` RPC trait:

- `pub trait EngineApi<Engine: EngineTypes>`
  - Methods are declared with `#[method(name = "...")]` and versioned explicitly.
  - Uses `Engine: EngineTypes` to abstract the versioned envelope types returned by `engine_getPayloadV*`.

Important notes from the trait definition:

- It intentionally avoids associated types inside the RPC trait because of `jsonrpsee` derive/bounds behavior.
- It includes spec references directly in doc comments (see "Execution APIs Spec References" section).

The same file also defines `pub trait EngineEthApi<...>` for the subset of `eth_` exposed on the auth server.

### 2) The RPC Implementation Layer (`reth-rpc-engine-api`)

`crates/rpc/rpc-engine-api/src/engine_api.rs` provides the concrete server implementation:

- `pub struct EngineApi<Provider, PayloadT: PayloadTypes, Pool, Validator, ChainSpec>`
  - Holds `Arc<EngineApiInner<...>>`.
  - Implements `reth_rpc_api::EngineApiServer<EngineT>` (the server-side trait generated by `jsonrpsee`).

Core dependencies injected into `EngineApiInner`:

- `provider: Provider`
  - Used for reading chain data and state for supporting endpoints like payload bodies.
- `chain_spec: Arc<ChainSpec>`
  - Used for fork activation rules (Shanghai/Cancun/Prague/Osaka gating, timestamp validation, etc).
- `beacon_consensus: ConsensusEngineHandle<PayloadT>`
  - Used to forward `newPayload` and `forkchoiceUpdated` to the Engine Tree.
- `payload_store: PayloadStore<PayloadT>`
  - Used to resolve payloads for `engine_getPayloadV*` and read payload timestamps.
- `tx_pool: Pool`
  - Used for blob retrieval endpoints (`engine_getBlobsV*`).
- `validator: Validator` (`EngineApiValidator<PayloadT>`)
  - Used to validate version-specific request fields and validate payload attributes.
- `metrics: EngineApiMetrics`
  - Per-method latency histograms and blob-related counters.

The implementation pattern is consistent across methods:

- RPC entrypoint (`impl EngineApiServer<...> for EngineApi<...>`)
  - Logs `trace!(target: "rpc::engine", ...)`.
  - Normalizes the request into internal typed payload data (e.g. wraps into `ExecutionData` + sidecar).
  - Calls a metered helper (`*_metered`) that records latency.
  - Delegates to `ConsensusEngineHandle` for `newPayload` and `forkchoiceUpdated`.

### 3) The Hand-off Boundary: `ConsensusEngineHandle`

`ConsensusEngineHandle` (defined in `crates/engine/primitives/src/message.rs`) is the bridge between the async RPC server and the synchronous engine handler thread.

- `ConsensusEngineHandle<Payload: PayloadTypes>` is basically a cloneable sender:
  - wraps `tokio::sync::mpsc::UnboundedSender<BeaconEngineMessage<Payload>>`.
  - provides async convenience methods:
    - `new_payload(payload) -> Result<PayloadStatus, BeaconOnNewPayloadError>`
    - `fork_choice_updated(state, payload_attrs, version) -> Result<ForkchoiceUpdated, BeaconForkChoiceUpdateError>`

RPC methods like `engine_newPayloadV3` ultimately call:

- `self.inner.beacon_consensus.new_payload(payload).await`

Likewise `engine_forkchoiceUpdatedV2` calls:

- `self.inner.beacon_consensus.fork_choice_updated(state, payload_attrs, version).await`

This boundary matters for debugging timeouts: responses are returned over a oneshot channel inside the message.

## Key Shared Types And Traits

### `EngineTypes`

Defined in `crates/engine/primitives/src/lib.rs`.

Purpose:

- Abstract over the *versioned payload envelope types* returned by `engine_getPayloadV1..V5`.
- Also implies `PayloadTypes`, which defines:
  - `ExecutionData` (the internal payload input, including sidecar fields)
  - `PayloadAttributes`
  - `BuiltPayload`

Key shape:

- `pub trait EngineTypes: PayloadTypes<...> + DeserializeOwned + Serialize`
- Requires `BuiltPayload` can be converted into each envelope type (`TryInto<ExecutionPayloadEnvelopeV*>`).

This is used by the RPC trait layer (to type the server trait and client stubs) and by the concrete RPC implementation.

### `EngineApiValidator`

Defined in `crates/engine/primitives/src/lib.rs`.

Purpose:

- Validate version-specific field presence/exclusion for both:
  - payloads received via `newPayload`, and
  - attributes received via `forkchoiceUpdated`.

Methods:

- `validate_version_specific_fields(version, payload_or_attrs) -> Result<(), EngineObjectValidationError>`
  - Used by `reth-rpc-engine-api` when handling `engine_newPayloadV*`.
- `ensure_well_formed_attributes(version, attributes) -> Result<(), EngineObjectValidationError>`
  - Used by `reth-rpc-engine-api` in `validate_and_execute_forkchoice`.

In `EngineApi::validate_and_execute_forkchoice` (`crates/rpc/rpc-engine-api/src/engine_api.rs`):

- Attributes are validated first.
- If attribute validation fails, Reth still forwards the forkchoice update *without attributes* (`payload_attrs = None`) to ensure forkchoice updates are not rolled back (matches spec requirement).

### `PayloadValidator`

Defined in `crates/engine/primitives/src/lib.rs`.

Purpose:

- Validate and convert `ExecutionData` into blocks, in the order expected by the Engine API spec.

Key methods:

- `convert_payload_to_block(payload) -> Result<SealedBlock<Block>, NewPayloadError>`
  - Pre-validation + computes hash, but does not recover tx signatures.
- `ensure_well_formed_payload(payload) -> Result<RecoveredBlock<Block>, NewPayloadError>`
  - Default implementation: `convert_payload_to_block` + signature recovery.

This trait is used inside the Engine Tree (via an engine-tree-specific validator wrapper).

### `ConsensusEngineHandle`

Covered above; it is the message-based bridge from the RPC layer into the Engine Tree.

### `PayloadStore`

Defined in `crates/payload/builder/src/service.rs`.

Purpose:

- Provide an async API for the RPC layer to fetch payloads and metadata from the payload builder service.

Key methods:

- `resolve(id) -> Option<Result<BuiltPayload, PayloadBuilderError>>`
- `payload_timestamp(id) -> Option<Result<u64, PayloadBuilderError>>`

`reth-rpc-engine-api` uses this for `engine_getPayloadV*` and for validating timestamp constraints before returning certain versions (e.g. Osaka restrictions on getPayloadV4).

## Engine Tree: Responsibilities And Flow

The Engine Tree is the in-process implementation that processes Engine API messages, executes blocks, tracks canonical state, and emits events.

The core handler is `EngineApiTreeHandler` in `crates/engine/tree/src/tree/mod.rs`.

### What The Engine Tree Owns

`EngineApiTreeHandler` (generic over node primitives, provider, payload types, validator, and EVM config) holds:

- `state: EngineApiTreeState`
  - `tree_state`: executed blocks, canonical head (in-memory tree)
  - `forkchoice_state_tracker`: tracks incoming FCU state
  - `buffer`: holds detached blocks / buffered payloads
  - `invalid_headers`: cache of invalid payload headers
- `consensus: Arc<dyn FullConsensus<...>>`
  - consensus validation integration.
- `payload_validator: V` (engine-tree validator)
  - validates and executes payloads.
- `payload_builder: PayloadBuilderHandle<T>`
  - used to start payload build jobs when FCU includes attributes.
- `persistence: PersistenceHandle`
  - writes canonical chain updates to DB / static files.
- `canonical_in_memory_state: CanonicalInMemoryState`
  - state view of canonical chain that is not yet persisted.
- `metrics: EngineApiMetrics` (engine-tree metrics)
- `engine_kind: EngineApiKind`
  - e.g. Ethereum vs OpStack behavior differences.

It runs in its own thread (see `spawn_new`): it blocks, receives messages, processes them, and optionally triggers persistence/backfill/download actions.

### Message Entry Points

Engine Tree processes messages of type `FromEngine<EngineApiRequest<...>, Block>`.

The relevant high-level operations:

- `on_new_payload(payload)`
- `on_forkchoice_updated(state, attrs, version)`

Both are called from inside `on_engine_message` (not shown in the excerpt, but this is the central dispatcher).

### `newPayload` Processing

`EngineApiTreeHandler::on_new_payload` (`crates/engine/tree/src/tree/mod.rs`) implements the core `engine_newPayload` semantics.

Key responsibilities:

1. Emit an engine event that a block was received:
   - `ConsensusEngineEvent::BlockReceived(num_hash)`.
2. Validate for invalid ancestors first (`find_invalid_ancestor`).
3. Perform *payload layout validation* via the payload validator.
   - The code comment explicitly calls out EIP-4844 "versioned hashes" checks (expected vs actual hash arrays).
4. Handle sync/backfill mode:
   - If backfill pipeline is idle: `try_insert_payload(payload)`
   - Else (during pipeline backfill): `try_buffer_payload(payload)`

Insert behavior highlights:

- `try_insert_payload` attempts to insert and execute the payload.
  - Returns `PayloadStatusEnum::Valid` when inserted or already seen valid.
  - Returns `PayloadStatusEnum::Syncing` when disconnected / missing parent.
  - On error, maps to appropriate invalid payload responses.

- `try_buffer_payload` buffers payloads during backfill.
  - Still runs a cheap well-formed conversion (`convert_payload_to_block`) so malformed payloads can be rejected even while syncing.

Canonicalization hook:

- If the payload is valid and matches the "sync target head" the handler may emit a `TreeEvent::TreeAction::MakeCanonical`.

Metrics:

- Records payload validation and total newPayload duration:
  - `self.metrics.block_validation.record_payload_validation(...)`
  - `self.metrics.block_validation.total_duration.record(...)`

### `forkchoiceUpdated` Processing

`EngineApiTreeHandler::on_forkchoice_updated` (`crates/engine/tree/src/tree/mod.rs`) implements the core `engine_forkchoiceUpdated` semantics.

Key responsibilities:

1. Record/advance forkchoice metrics and state tracking.
2. Pre-validate forkchoice state:
   - Reject `head_block_hash == 0` as invalid state.
   - Reject if connected to previously known invalid ancestor.
   - Return `Syncing` if pipeline backfill is in progress (needs exclusive DB access).
3. Fast path if head is already canonical:
   - Update safe/finalized tracking.
   - If attributes provided: process attributes and start a payload build.
   - Else return `VALID` with `latestValidHash = head`.
4. Apply chain updates:
   - If head is a canonical header and config/engine-kind requires, it may unwind state to that canonical ancestor (notably for OpStack or if configured).
   - Else, if head is in the in-memory tree (sidechain), compute a chain update / reorg and apply it.
5. Fallback: if head block is missing, request downloads/backfill.

Payload attributes:

- FCU attributes are the trigger to start building a payload via payload builder handle.
- Engine-kind (OpStack) and config flags affect whether attributes are always processed even if head is already canonical.

### Persistence And Backfill

The Engine Tree is designed to:

- Accept incoming Engine API messages while backfill sync or persistence is happening.
- If a large batch of blocks arrives, process in bounded chunks and requeue the remainder via its own `incoming_tx` to stay responsive.

The `run` loop:

- Waits for either:
  - an engine message, or
  - a persistence completion (biased to handle persistence completion first).
- After each event, tries to `advance_persistence()`.

## Node Wiring: From Node Startup to Engine Tree

At runtime, the system wiring looks like this:

1. Node launch creates a channel for Engine API messages:
   - `(consensus_engine_tx, consensus_engine_rx) = unbounded_channel()`.
2. The RPC add-ons context gets a `ConsensusEngineHandle::new(consensus_engine_tx.clone())`.
3. The authenticated RPC server (authrpc) is built with the `EngineApi` implementation, which holds that handle.
4. The engine service builds the Engine Tree and runs it:
   - `EngineService::new(...)` spawns `EngineApiTreeHandler::spawn_new(...)`.
   - It wraps the tree in an `EngineHandler` + `ChainOrchestrator` with optional pipeline backfill (`PipelineSync`).

This is shown in `crates/node/builder/src/launch/engine.rs` and `crates/engine/service/src/service.rs`.

## Metrics And Observability

There are two major layers of metrics relevant to Engine API:

### RPC-level Engine API Metrics (`engine.rpc.*`)

Defined in `crates/rpc/rpc-engine-api/src/metrics.rs`.

- `engine.rpc.*`: per-method latency histograms
  - `engine.rpc.new_payload_v1` ... `engine.rpc.new_payload_v4`
  - `engine.rpc.fork_choice_updated_v1` ... `engine.rpc.fork_choice_updated_v3`
  - `engine.rpc.get_payload_v1` ... `engine.rpc.get_payload_v5`
  - bodies and blobs latencies

- `engine.rpc.blobs.*`: blob request counters

These help you answer "is the RPC handler slow" vs "engine processing is slow".

### Engine Tree Metrics (`consensus.engine.beacon.*`, `blockchain_tree.*`, `sync.block_validation.*`)

Defined in `crates/engine/tree/src/tree/metrics.rs`.

Notable signals:

- `consensus.engine.beacon.*`
  - response counters for newPayload and FCU by status
  - response delivery failure counters:
    - `failed_new_payload_response_deliveries`
    - `failed_forkchoice_updated_response_deliveries`
  - block insert duration, persistence duration

- `sync.block_validation.*`
  - payload validation duration histograms
  - state root computation timing
  - post-execution validation timing

- `blockchain_tree.*`
  - `reorgs`, `latest_reorg_depth`
  - canonical chain height
  - safe/finalized heights

## Mental Model: End-to-End Call Path

### `engine_newPayloadV*`

- HTTP request hits authrpc server (jsonrpsee) -> `EngineApiServer::new_payload_v*`.
- Implementation wraps request into `ExecutionData` and validates fork-specific fields via `EngineApiValidator::validate_version_specific_fields`.
- Calls `ConsensusEngineHandle::new_payload`.
- Engine Tree receives message, validates/executes payload, updates tree, returns `PayloadStatus`.

### `engine_forkchoiceUpdatedV*`

- HTTP request -> `EngineApiServer::fork_choice_updated_v*`.
- `EngineApi::validate_and_execute_forkchoice` checks attributes via `EngineApiValidator::ensure_well_formed_attributes`.
  - If invalid attributes: still forwards FCU with `None` attributes.
- Engine Tree updates canonical head / safe / finalized, and potentially triggers payload building.

## Practical Debugging Pointers (Engine API <-> Tree Boundary)

- If RPC logs show "Serving engine_newPayloadV*" but no engine progress:
  - suspect Engine Tree handler thread blocked (persistence/backfill/DB contention) or message channel issues.

- If the CL times out and drops the request:
  - look at tree metrics:
    - `consensus.engine.beacon.failed_new_payload_response_deliveries`
    - `consensus.engine.beacon.failed_forkchoice_updated_response_deliveries`

- If you see many `Syncing` statuses:
  - likely missing parents, backfill in progress, or head not downloaded yet.
  - confirm engine tree metrics and logs (`target: "engine::tree"`).

- If payload attributes are being rejected:
  - expect errors derived from `EngineObjectValidationError` / `InvalidPayloadAttributesError`.
  - the forkchoice update itself may still be applied without starting a payload build (by design).
